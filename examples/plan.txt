## Purpose

This note gives RAs and instructors the teaching plan for the recurring NHANES Health Equity Dashboard case study. The case study should function as a course spine: students revisit the same app, data, and workflow from different angles as their skills mature. It should not become a second term project.

## Pedagogical Design

The strongest use of this case study is incremental. Students should first learn to inspect and document a provided artifact, then audit and compare code, then critique visual and KT choices, and only later perform a fresh-run reproducibility stress test.

The progression is:

- Weeks 1-2: provenance, ethics, folder structure, relative paths, and rendering; no app run instructions.
- Weeks 3-5: data loading, missingness checks, AI audit comments, documentation-only Git changes, and R/Python parity checks using the CSV snapshot.
- Weeks 6-7: visualization critique, flawed-plot audit, EDA, Table 1, and planted-error audit.
- Week 8: first week where running the Shiny app is central.
- Weeks 9-10: slides, reports, source notes, limitations, and audience-specific communication.
- Week 11: fresh-session reproducibility testing and optional rebuild from CDC if internet access is available.

The cached RDS is the default classroom path. Rebuilding from CDC through `nhanesA` is valuable, but it is network-dependent and can be slow. Treat CDC rebuilds as an instructor demo or Week 11 challenge unless the course explicitly allocates time for them.

## Week-by-Week Instructor Notes

Week 1 introduces the case study through the Data Intake Card. Keep the focus on provenance, stewardship, and KT framing. Students do not need to run the app.

Week 2 uses the case study to make repo structure concrete. Students should locate the app, data, script, and snippet; confirm that paths are relative; and render the book.

Week 3 uses the CSV snapshot as a code-reading and data-inspection object. Students load, inspect, summarize, and ask AI to comment on code, then audit the comments against the actual operations.

Week 4 uses the case study for Git practice. The safest PR-sized change is documentation-only: label, caption, README wording, or a limitation note. Avoid asking students to add new analytic variables during the Git week.

Week 5 uses the CSV snapshot for R/Python parity. The goal is not Python mastery; it is learning how plausible outputs can diverge because of missing values, data types, or grouping choices.

Week 6 uses the worked ggplot example, flawed instructor plot, and visual-audit activity. Prefer instructor-provided flawed examples over asking students to invent misleading visuals from scratch.

Week 7 uses the worked Table 1 example and planted-error starter. Survey weights, strata, and PSU columns can be identified, but design-based standard errors should be instructor/demo material unless already taught.

Week 8 is the first app-forward week. Students should run the app, identify an audience, and improve one audience-facing label, help text, caption, or interpretation note. Deployment should remain optional unless explicitly assigned.

Week 9 uses one dashboard plot or table as the basis for a short slide explanation. Students should include a plain-language takeaway, a limitation, and a source note.

Week 10 turns the dashboard into a companion report. The report should document data, methods, limitations, and source notes rather than duplicating the dashboard interface.

Week 11 stress-tests reproducibility. Students should launch the app from a fresh session, confirm the cached RDS path, and optionally rebuild from CDC if internet access and time allow.

## What RAs Should Watch For

- Students may confuse the cached case-study dataset with raw NHANES microdata.
- The app's Download CSV button exports the currently summarized table output, not raw NHANES microdata.
- The CDC rebuild path requires internet access and the `nhanesA` package.
- Week pages should include the shared snippet rather than duplicating instructions.
- Weeks 1-2 should not instruct students to run the app.
- Week 8 is the first week where app running is central.
- Student changes should stay small unless the instructor explicitly assigns a dashboard feature.
- Relative paths are part of the lesson; discourage absolute machine-specific paths.

- Weeks 1-11 each include a short case-study touchpoint.
- The case-study folder contains runnable app code, cached data, rebuild script, shared snippet, and README.
